    Validation¶

    This page is for whoever has to sign off on using OpenDNA for real work: a QA reviewer, a core facility lead, somebody writing a methods section. It states what has been checked, by whom, how, and what has not been.

    It is not a claim that OpenDNA is validated for your purpose. Validation is against an intended use, and only you know yours. What this gives you is the evidence to do that assessment, and an honest account of where the evidence runs out.

    Everything below was measured on the hardware named with it. Where a number comes from one machine, it says so, because a number from one machine is weaker evidence than it looks.

    What the software is¶

    Four small networks on top of frozen ESM-2 embeddings. The language model is never fine-tuned, so each head is a few hundred kilobytes of weights over a 568 MB embedding model that is itself a published third-party checkpoint (facebook/esm2_t30_150M_UR50D).

    Head Predicts Honest out-of-domain performance
    disorder per-residue intrinsic disorder AUROC 0.941 on CAID3 Disorder-PDB
    burial per-residue relative solvent accessibility see model card
    solubility whole-protein solubility, E. coli cell-free see model card
    stability ΔΔG for a named point substitution ~0.44 Spearman out of domain

    The stability figure is the one to read carefully. 0.44 Spearman makes it a ranking signal for prioritising constructs, not a measurement of ΔΔG. Each head's model card states its own limitations and the CLI copies them into every output file, so a number cannot travel without them.

    There is no fallback anywhere. A missing head is an error naming the files it looked for. A sequence too long for the solubility head is refused rather than scored by a different method. Nothing in OpenDNA estimates a property without a trained model for it.

    Can I identify what I ran?¶

    Yes, and it is checkable rather than asserted.

    Each head records a semantic version, a build id digesting everything that determined the weights (the dataset manifest, the hyperparameters, the embedding model, the training code version), and the SHA-256 of its weights file. opendna models rehashes the weights and reports verified, NOT VERIFIABLE (metadata predating hashes) or CORRUPT.

    opendna models --lock models.lock    # pin
opendna models --check models.lock   # fail unless the install is still that

    --check catches a retrain that kept the same version number, because the build id changes even when the version does not. Commit the lockfile beside the analysis it produced.

    Checked: appending one byte to a weights file is reported CORRUPT, makes opendna models exit 3, and makes opendna predict refuse before loading anything. A head whose build id differs from a lockfile fails --check with both values named.

    Can I prove it works on this machine?¶

    opendna selftest

    Seventeen checks over a bundled ubiquitin sequence, through the same code path predict uses rather than a parallel harness. Eight are invariants that hold for any build of these heads — one value per residue, probabilities within [0,1], accessibility within [0,1.25], the hydrophobic core less accessible than the chain-forming lysines, L8P more destabilising than L8M, and a second identical run giving identical values. Nine are numbers recorded from named builds, with tolerances.

    A pinned number is checked only against the build it was recorded from. Against another build it reports not checked and names both, because nobody has measured what that head does on this fixture. A retrain is therefore expected to leave those unchecked until new values are recorded; the invariants still run.

    Checked, and this is the part worth reading: burial's weights were copied over the disorder head and the metadata rewritten so the file hashes correctly. opendna models passed that installation completely clean — every head verified. The self-test failed three pinned checks and exited 5. A checksum cannot detect a model that is intact and wrong; this can.

    The fixture's positions were chosen for that case. Disorder and burial share an architecture and differ only in the squash on the output, so at some positions their numbers agree to 0.004 and a pin there would survive the swap. The positions used are ones where the two disagree by more than a quarter.

    Tolerances are a judgement, not a measurement. They were set wide enough to absorb a different BLAS or device and narrow enough that a wrong model fails. A failure that lands just outside one is worth reporting, not widening.

    How reproducible are the numbers?¶

    Exactly this much:
    Same input, same device, same --batch-tokens byte-identical
    Same input, same device, different --batch-tokens ~0.2% of values differ
    Same input, CPU vs GPU ~0.3% of values differ

    Measured on 200 sequences and 35,033 residues. Across devices, 102 of 35,033 disorder probabilities differed, by at most 0.0001 and 0.0000003 on average. That is the f32 rounding floor, not a disagreement about biology, and it moves no disorder call at any sensible threshold.

    It does mean a result file from a GPU and one from a CPU are not the same bytes. Do not diff them and do not compare their checksums.

    The cause in both cases is the order of floating-point summation: padding changes it, and so does different silicon. Device and batch size are recorded in every run manifest, which makes the table above checkable — two manifests agreeing on input digest, head build, device and batch size should have produced the same output digest, and if they did not, something is wrong worth finding.

    Driving one model from several threads at once on CUDA perturbs the low bits, because cuBLAS picks differently shaped reductions under concurrent load. The CLI is serial, which is why.

    Checked: byte-identical repeat runs on both CPU and an RTX 2000 Ada. All seventeen self-test checks pass on both, with values pinned on CPU.

    Do the probabilities mean anything?¶

    For the disorder head, now yes, and the correction was substantial.

    The head is trained with weighted cross-entropy so that it does not predict "ordered" everywhere. That helps the ranking and inflates the probabilities, and the inflation was never measured. It is large:

    the head said actually disordered
    0.95 65%
    0.85 50%
    0.75 32%
    0.55 13%

    Expected calibration error on the held-out split was 0.217. A Platt map (p = sigmoid(0.7237·logit − 1.5665)) fitted on the validation split brings it to 0.032, and the Brier score from 0.168 to 0.099. The map is monotonic, so AUROC is identical before and after — 0.8833 on the internal test split either way, which is the check that nothing was traded away.

    It also moved the decision threshold, which matters more than the probabilities for anyone thresholding them. 0.5 was a convention and was never right for this head: on the raw scale its own optimum is 0.73. On the calibrated scale the threshold chosen on validation is 0.34, and it scores MCC 0.5213 on test against 0.4934 for the old raw-0.5 default — close to the 0.5284 upper bound that could only be found by looking at the test labels. Both the map and the threshold are recorded in the head's metadata, and the CLI and the desktop application both read them from there rather than compiling in a number.

    Because the head now reports different numbers from the same weights, it is a different model: its version went to 1.1.0 and its build id changed, so a lockfile taken before the calibration correctly fails against it.

    The threshold is a property of a distribution, not of the head, and this one does not suit every set. On the CAID3 reference set, MCC falls from 0.7292 to 0.7096, F1 from 0.8182 to 0.7788 and balanced accuracy from 0.8777 to 0.8250 at the new threshold — because 0.34 calibrated is about 0.78 raw, and that set wants a lower cut than ours does. The reason is measurable rather than hand-waved: 31.6% of CAID's assessed residues are disordered against 17.9% of our internal test split's, so it is nearly twice as positive a set, with a PDB-derived definition of disorder rather than DisProt's. AUROC and AUPRC are identical (0.9410 and 0.8996), which is why those are the figures to compare against published work. If you threshold these probabilities for a decision of your own, the right cut depends on your class balance and on what a false positive costs you. Calibration is what makes that reasoning possible; it does not make the choice for you.

    What this is calibrated against is the annotation, not nature. DisProt records disorder demonstrated experimentally and unannotated residues are treated as ordered in training. If that under-reports disorder — and it does, by an unknown amount — these probabilities inherit it. A calibrated 0.3 means "three in ten of residues like this are annotated disordered in DisProt", which is a weaker statement than it looks.

    Intervals on every figure above are bootstrapped over proteins, not residues. Neighbouring residues almost always share a label, so resampling residues would report an interval several times too narrow.

    How wrong is a regressor's number likely to be?¶

    Each of the three regressors now reports an interval beside its point, fitted by split conformal prediction on the validation split and measured on the held-out one:

    Head 90% interval Coverage achieved Held-out MAE
    stability ±1.33 kcal/mol 93.7% 0.53 kcal/mol
    solubility ±38.9 percentage points 91.1% 18.8 pp
    burial ±0.237 RSA 87.5% 0.115 RSA

    Read the stability row before acting on a ddG. A predicted −0.78 kcal/mol comes with an interval of −2.11 to +0.55, which spans zero: at 90% confidence that head cannot tell you whether the mutation is destabilising at all. A prediction of −1.59 gives −2.92 to −0.26, which does not. That distinction is the useful content, and a point estimate alone hides it.

    Read the solubility row the same way. ±39 percentage points on a 0–100 scale is most of the range, which is the honest measure of how much a single solubility number is worth. Intervals there can extend past 100%, because the head is an unbounded regressor that was never constrained to the physical range — an interval reaching 139% is the head saying it does not know.

    Coverage is measured, not assumed, and burial falls short. A conformal guarantee assumes the calibration and held-out sets are exchangeable. This project's splits are deliberately not: the dataset builder clusters by sequence identity so near-identical proteins cannot straddle a split, which makes the held-out set systematically more distant than a random sample would be. That is the right way to build the splits and it costs the guarantee its exactness. Burial achieves 87.5% where 90% was asked for, 76.0% where 80% was, and 43.3% where 50% was — short at every level.

    Coverage is also marginal, not conditional. The half-width is constant, so the interval is wider than needed where the head is reliable and narrower than needed where it is not. For burial at the 90% level, coverage runs from 96.8% for residues predicted to be buried down to 79.1% in the middle of the range. Somebody holding a mid-range prediction has a 79% interval labelled 90%. Each model card lists the conditional coverage by band.

    One more caveat specific to stability, and it is worse than an earlier version of this page said. Its 37,983 calibration residuals come from the validation split, which the dataset manifest records as 18 sequence-identity clusters of wild-type proteins; coverage was then measured on a test split of 24. This page previously said 36, a figure nothing supports — the manifest is the source, and it is in datasets/cards/stability/manifest.json. Residuals from one wild-type protein are correlated, so each quantile rests on something nearer 18 independent observations than 37,983, and coverage on a protein unlike those 18 may be worse than the table says.

    Should I trust every residue equally?¶

    No, and the disorder head now says which ones. How far the calibrated probability sits from the decision threshold orders residues by how likely the call is to be wrong, measured on the held-out split:

    Minimum confidence Residues kept Error among them
    0.00 (everything) 100% 15.7%
    0.05 89% 12.0%
    0.10 80% 9.3%
    0.20 66% 6.5%
    0.25 57% 5.3%

    The signal captures 55% of the error reduction an oracle shows is available — an oracle being a rule that discards exactly the wrong calls. Half of what is there. Worth having, not a guarantee.

    Every disorder output carries a confidence column. predict --min-confidence <c> additionally marks the rows below a cut-off in a low_confidence column and prints what that cut-off was measured to buy. Nothing is ever removed: a table quietly missing rows looks exactly like a complete one, and the cut-off is the caller's because the right one depends on what a wrong call costs them.

    A signal that failed, recorded so nobody re-tests it. The obvious out-of-domain proxy — whether the 5-mer centred on a residue was seen in training — carries no information about error. Its area under the risk–coverage curve was 0.171 against 0.158 for discarding residues at random, so marginally worse than nothing, despite 44.9% of held-out residues sitting on an unseen 5-mer. Error on novel k-mers is not higher than on familiar ones. A plausible story about why a signal should work is not evidence that it does.

    Can I continue a run that was interrupted?¶

    Yes, and the thing worth checking is not that it continues but that continuing gives the same answer as not having stopped.

    --checkpoint <file> records results as they are produced and syncs them to disk after every chunk of --chunk sequences. Running the same command again continues from the last complete chunk. The results file is written only when the run finishes.

    Verified byte-identical. On a twelve-sequence file predicted in chunks of four, a checkpoint was cut back to one complete chunk plus a half-written record — what a process killed mid-write leaves behind — and the run was started again. It reported the incomplete tail, dropped it, continued from chunk one, and produced the same 854 rows as the uninterrupted run, byte for byte, with the same output digest recorded in both manifests. The checkpoint files themselves also ended up identical.

    This holds because the chunk boundaries are fixed and recorded rather than falling wherever the interruption did. Sequences are batched for embedding within their chunk, and batch composition changes the order of floating-point sums, so an arbitrary cut would not reproduce. The cost is that the chunk size is itself a setting that changes the numbers:
    any --chunk, with --batch-tokens 0 identical to a run with no checkpoint
    --chunk 1 or 4, at the CPU default of 8192 1 of 853 burial values differs, by 0.0001

    That is the same mechanism and the same order of magnitude as the batch-size effect already measured above, and it is why the chunk size is recorded in every run manifest and compared by opendna merge.

    Resuming is refused, naming the field that differs, when the input bytes, the chunk size, the head build, the head's weights digest, the embedding model, the device, the batch size, the mutation file or the confidence cut-off is not what the checkpoint was written with. A file that is not a checkpoint is refused without being modified.

    Can I run it without a network?¶

    opendna stage --to /mnt/usb/opendna-models   # on a connected machine
opendna --models ./opendna-models --offline selftest

    stage writes one directory holding the four heads, their model cards, the embedding model's own files, models.lock, a sha256sums.txt in the format sha256sum -c reads, and a LICENSES.md. It copies what the staging machine already resolved rather than re-fetching on the target, so the bundle is what was tested. It refuses to stage an installation that does not verify.

    --offline is a hard promise: nothing reaches the network, and a missing embedding model is an error naming the two files it wanted and the command that makes them, rather than a stall.

    Checked: with HF_HOME pointed at an empty directory so the cache held nothing, --offline passed all seventeen self-test checks against a staged bundle and produced disorder values identical to the online run. sha256sum -c sha256sums.txt verified all fourteen files (four heads with weights, metadata and card each, plus the embedding model's two). With nothing staged, --offline exits 3 with the staging instructions.

    What does a failure tell my pipeline?¶
    0 it worked —
    1 an unanticipated failure report it
    2 the command asked for something that does not exist fix the command
    3 the installation is wrong fix the machine; retrying will not help
    4 the data is wrong fix the input; retrying will not help
    5 the checks ran and did not hold do not use results from this machine

    Anything not classified is 1, deliberately: a failure nobody anticipated is not one a caller can be told how to handle.

    predict streams results to standard output, so a failing run leaves standard output empty — a pipe collecting results never receives an error as though it were data.

    Checked: all twelve cases in tests/exit_codes.rs, against the compiled binary, with the corrupt and swapped fixtures built from a copy of the real models.

    Can I show what produced a result?¶

    Every run that writes an output file writes out.manifest.json beside it: input path and SHA-256 of the bytes read, output path and SHA-256, row count, head task/version/build/weights-hash, embedding model, device, batch size, UTC start, wall-clock duration, the arguments as given, the head's licence, and the model card's limitations.

    The input is hashed from the bytes in memory rather than by re-reading the file, so the digest describes what was used even when the input arrived through a pipe and has no path.

    The embedding model is not hashed by default: at 568 MB it costs about as long as a small run. A staged bundle already records the digest, so a staged install carries it for free; otherwise the field is null and sha256_source says why. An absent field with a reason is honest. A missing field somebody assumes was checked is not.

    What are my obligations if I pass this on?¶

    Three heads are Apache-2.0. The solubility head is CC BY-SA 2.1 JP: it is trained on eSOL, which carries that licence, and because the licence is share-alike — and because whether trained weights are a derivative work of their training data is an open legal question this project will not answer in its own favour — the weights carry the same terms.

    A staged bundle is a redistribution. opendna stage writes a LICENSES.md grouping heads by licence and stating when passing the bundle on carries obligations, and each card travels beside its weights with the attribution its licence requires. Required attribution for eSOL: "eSOL © Hideki Taguchi (Tokyo Institute of Technology) licensed under CC Attribution-Share Alike 2.1 Japan".

    All of it is read out of the model cards rather than written into the program, so a notice cannot claim terms the file beside the weights does not. A head whose card declares no licence is reported as unstated and treated as possibly obliging.

    Can several runs go at once on one machine?¶

    Only against a staged bundle. Measured:
    Two runs loading the embedding model through the Hugging Face cache one failed, exit 3
    Three runs against a directory produced by opendna stage all three fine

    The cache is not safe for two processes to read at the same time; on Windows the second is refused the weights file by the operating system. A staged bundle is opened read-only and shares without trouble. So a node running several parts of a split in parallel needs opendna stage once and then --models <bundle> --offline on each task, which is what the cluster section of the CLI README now says. The error a failed concurrent run prints names this as the likely cause.

    What has not been checked¶

    Stated plainly, because a validation document that lists only successes is marketing.

    • One machine. Every number here comes from a single Windows workstation with an RTX 2000 Ada. CI builds on three operating systems, but the measurements above were not repeated on them. Cross-platform numerical agreement is untested.
    • No GPU other than one. The finding that batching costs time on a GPU is from that one card. Another may behave differently, which is why --batch-tokens is a flag.
    • Timing figures are approximate. The CPU gain from batching measured a tenth in one session and a sixth in another. Two earlier attempts, taken while a compile competed for the cores, produced an overstated figure and then none at all. If you benchmark, interleave the settings and report the spread.
    • Tolerances in the self-test are a judgement, set on one machine, not a measured bound on acceptable variation.
    • No clinical or diagnostic validation of any kind. These are research tools. The stability head in particular is a ranking signal at ~0.44 Spearman out of domain.
    • Metrics on each head's own test split are not comparable to published leaderboard figures without running that leaderboard's protocol. The disorder head's CAID3 number was produced by running the CAID protocol; the others' were not.
    • No signed installers. Binaries are unsigned, so operating systems will warn. Code-signing certificates have not been obtained.
    • The regressors' intervals rest on an assumption the splits break. See the section above. Conformal coverage assumes calibration and held-out sets are exchangeable; clustering by sequence identity makes them deliberately not. The achieved coverage is measured rather than assumed, and for burial it falls short at every level.
    • Resuming was checked on small runs, on the CPU only. The byte-identical result above comes from files of two to twelve sequences predicted in two to twelve chunks, with a real process kill in one case and a hand-truncated checkpoint in the others. All four heads were covered. What was not exercised is the thing the feature is for: a run of tens of thousands of sequences interrupted hours in. Nor was any of it repeated on the GPU, where the batch default differs.
    • Nothing detects out-of-domain input. The disorder head reports a confidence that predicts error (see above), but that is not the same thing: a sequence from a family it never saw can still produce a confident wrong answer. The one out-of-domain proxy measured here, whether a residue's 5-mer was seen in training, carried no information about error at all.

    Reproducing the checks¶

    opendna models --check models.lock   # the install is what it was
opendna selftest                     # it computes what it recorded
opendna --device cpu selftest        # and on the CPU too, where a GPU exists
cargo test --workspace               # unit and contract tests
cargo test --release -p opendna-cli -- --ignored   # the two needing inference

    The exit-code test needs trained heads installed and skips with a message when they are absent, because a test that fails on every machine without them gets disabled and then checks nothing at all.
